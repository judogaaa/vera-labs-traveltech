# Безопасность

Не публикуйте токены, конфигурации серверов, содержимое реальных баз, пользовательские фотографии и переписку в Issues или Pull Requests. Для воспроизведения используйте отдельные тестовые данные.

При обнаружении уязвимости используйте приватный Security Advisory во вкладке Security этого репозитория. Если приватная форма недоступна, создайте Issue только с просьбой предоставить закрытый канал связи, без подробностей эксплуатации и секретных значений.

При утечке собственного ключа немедленно отзовите его у провайдера, выпустите новый и проверьте журналы доступа. Удаление файла из последнего коммита не очищает предыдущие коммиты.

Публичная версия имеет отдельную историю. Рабочие базы, платёжные ключи и настройки действующих сервисов сюда не входят. `.env` хранится только локально; `.env.example` содержит безопасные примеры.

## Ограничения модели доступа Trip API

- Изоляция поездок привязана к подписанной HttpOnly cookie-сессии, а не к аккаунту. Это минимально безопасная схема для локального демо: у кого есть cookie, тот видит поездку. Cookie не содержит долгоживущих секретов и подписывается серверным ключом.
- Реестр сессий и владельцев поездок файловый и рассчитан на один хост. Несколько воркеров на одной машине работают, несколько хостов — нет: замените реестр на Redis/БД и оставьте тот же контракт подписи.
- Для HTTPS включайте `TRIP_COOKIE_SECURE=1` (или полагайтесь на автоопределение схемы) и задайте `TRIP_SESSION_SECRET` вне репозитория.
- CSRF-токен выдаётся `GET /api/trips/session`; без него `POST`/`PATCH`/`DELETE` отклоняются. Дополнительно проверяется `Origin`, если браузер его прислал.
- Ограничения частоты и параллелизма действуют в пределах процесса. Публичный интернет-хостинг требует общих лимитов на reverse proxy.
- `TRIP_SESSION_FILE`, `TRIP_SESSION_SECRET_FILE` и `data/trips/` не коммитятся и не должны попадать в артефакты CI.
